- **TG-P1-2 (P1) — a tap never drops a sibling.** The root cause was a shared-file read-merge-write: `recordDecision` read `decisions.json`, merged, and rewrote it — racing the console's unlocked full-snapshot `writeDecisions` (R25) and missing a decision stranded in a recoverable claim. Fixed by making a tap write its OWN file: `taps/<sha256(itemId)[:32]>.json` (a single-decision doc). A tap no longer touches `decisions.json`, so it can collide with neither the console snapshot (a different file) nor a sibling item (a different file) nor the claim (a different file). `readDecisions` and `consumeDecisions` FOLD `decisions.json` + the claim + every tap, latest-per-id, via the pure `foldDecisionDocs` (union by id; a tap wins an equal-second tie — the targeted single-item action is the more recent intent). Both r2 counterexamples are now regression tests: **A** (a decision stranded in a recoverable claim after a faulted consume) and **B** (a tap and a concurrent console full-snapshot write) BOTH survive. Taps are read under the consume lock (serialized vs a seal) and dropped only after the batch seals (a fault before the seal leaves them recoverable). R25 is untouched — `writeDecisions` stays an unlocked full-snapshot replace.
- **TG-P2-3 (now P1) — a callback uniquely binds its batch.** The ref's batch hash is widened to 32 hex (128-bit: a birthday collision is ~2^64 batches), and `resolveRef` REJECTS an ambiguous hash — it counts matches and returns null on `>1`, never first-hitting a wrong batch. The callback stays `d|<32hex>.<idx>|<verdict>[|<scope>]` ≈ 55 bytes ≤ 64 (selftest asserts).
- **TG-P2-1 (P2) — a read failure keeps the retry obligation.** `listBatchesStrict` + `readTaps` PROPAGATE a dir/file read error (never fold it to `[]`); `resolveRef` returns null ONLY on a CONFIRMED-unresolvable ref (no hash match, out-of-range index, or ambiguous), and a store read error THROWS. The driver treats a throw as transient — it STOPS the poll WITHOUT advancing the offset, so the tap is retried; a chmod-000 batches dir can no longer turn an approval into a permanent "expired" skip. (`listBatches` stays best-effort `[]` for the console index.)
- **TG-P1-1 (now P2) — the write boundary enforces scope too.** `writeDecisions` (the console path) now runs `enforceScope` against the REAL item before persisting — a hard-gate item can never be SAVED with a `this-chat`/`always` grant, from console or TG. The consume-side clamp (`resolveBatch`) remains the backstop.

## What this is
The Telegram USER-ENTRY, v1 = notify + collect-approvals, NEVER executes. Per the user's entry-layer ruling: an entry READS the core's frozen projections and WRITES the single decision ledger — zero business logic; console + TG are same-source, no fork; adding an entry does not change the core.

## Deliverables
- **CORE — decision-batch.ts (shared by every entry):** `ApprovalScope` (once/this-chat/always) on `Decision`; `hardGate` on `DecisionItem`; pure `allowedScopes(item)` — a hard-gate (spend/publish/irreversible) item offers ONLY `once`, never `always` (R16). Validators accept the optional fields; `scope` kept only on `approve`.
- **CORE — morning-digest.ts:** pure `composeDigest` (the once-generated morning brief; alerts lead; quiet-night explicit). Entries are delivery ends, not generators.
- **TG pure core — tg-entry.ts:** `renderProjection(proj) -> RenderSpec` (multimodal: `message` / `photo` gauge-card / `document` / pinned RED alert; decision items carry the scope keyboard from `allowedScopes`); `parseUpdate(update, allowlist, nowSec)` (allowlist the `chat_id` FIRST, map a tap to a one-decision `DecisionsDoc`; off-allowlist / typed-reply / malformed -> ignore); `encodeDecisionCb` / `parseCallback`. No IO; never changes a projection (image = entry-side render).
- **Thin driver — scripts/swarm-tg-entry.ts:** DORMANT behind `SWARM_TG_ENTRY`; token on STDIN -> 0600 (never argv/env, vm-ctl §creds); long-poll `getUpdates` -> `parseUpdate` -> `writeDecisions`; notify new batches; `answerCallbackQuery` ack; re-reads the allowlist each loop.

## Red lines (held)
- v1 EXECUTES NOTHING — a verdict is only WRITTEN to the ledger; the coordinator's R17 chain re-injects. The driver has no command path.
- `chat_id` ALLOWLIST gates every inbound before anything is read; TG text is untrusted.
- Single truth / no fork: a sealed batch REFUSES a second entry's write (`writeDecisions` throws `already consumed`) and `consumeDecisions` is terminal — whoever decides first wins, the other entry is a no-op (proven bidirectionally in selftest).
