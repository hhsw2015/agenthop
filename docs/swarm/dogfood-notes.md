# Dogfood 笔记:用蜂群协作模式开发蜂群本身

日期:2026-10-03,持续更新。性质:**经验记录,非契约**。本项目的设计-审查-实现正在用它自己设计的团队协作模式跑(多会话分工、总线消息、流水 review、异构对抗审查),这里逐条记下真实协作暴露的成功与失败,作为实现对应机制时的第一手参考。每条标注它印证或挑战的契约条款。

## 00. 递归自升级原则(用户定调,2026-10-03)

> **蜂群用自己的协作模式开发蜂群本身;协作暴露的每一条经验(成功与失败)回流为流程与契约的改进;改进后的流程再去跑下一轮开发。** 鸡生蛋、蛋生鸡——这个闭环就是蜂群的持续进化能力,它比任何单项机制都重要,因为所有机制都可以被它迭代掉。

这不是比喻,是已经在跑的回路,本文件就是回路的载体。闭环的四步:

```text
跑(用当前流程协作开发) → 记(真实暴露的 S/F 条目,§1/§2)
  → 改(回流:契约勘误/机制排期/验收补条目,§3) → 再跑(改进后的流程跑下一轮)
```

已完成的回路实例(证明闭环真转):
- F1 身份漂移(5 次实测)→ 投影 memberId 稳定性升优先级 + C1 验收加「句柄漂移后仍可达」→ 下一轮实现照此做。
- S8 裁决者可错 → 实例二:T1 复审中 Codex 发现冻结契约自身的分类表矛盾(permanent 行漏来源限定)→ 契约勘误落盘 → 实现照勘误后的表修。审查层审出了契约层的 bug,回流闭环跨了两层。
- S8 实例三(同时是新失败模式 **F8:裁定-勘误解耦**):设计侧给实现下裁定时忘了同步勘误契约,实现注释领先于契约文字;复验的 Codex 拒绝凭实现注释改探针,倒查裁定来源才补上勘误。教训:**裁定消息与契约勘误必须是同一个动作**,不同步 = 给下一个审查者埋「两个真相」。机制化对应:§2.6 的「规范性决定必须入账」,人肉流程同样适用——裁定没落进契约就不算裁定完成。
- F3 静默停摆 → jobStatus.blocked 带卡点名进投影 schema → viz 渲染后人能看见「谁在等谁」。

机制化方向(把回路从人肉变成蜂群自己的能力,排 T3 后):
- **经验条目是一种业务产出**:S/F 条目本质上是 review 节点的副产物,未来 worker/review 节点的 result.json 可带 `lessons[]` 字段,O1 照常收割,synthesis 节点定期把 lessons 聚合成流程修订提案(走计划修订,人放行)。
- **契约是可演进的冻结**:勘误(澄清矛盾)随时可做、双审查方记录即可;协议变更走重开审查。这条已经实践了一次,规则留此。
- **改进的验收也要可失败**:每条回流改进必须落到「验收条目/schema 字段/契约文字」三者之一,落不下去的经验是感想,不进 §3。

## 1. 验证成功的(实现时可引用为「已在真协作中跑通」)

- **S1 复述再开工(team-collab §4.5)**。实现会话每轮先说「我打算这么切,你裁」再动手(T1 的 V4 边界、retry 活性的 (i)/(ii) 选择)。全程零方向性返工。一行成本换掉最大失败类,实证有效。
- **S2 决策权三分自然涌现(§4.5 decisionRights)**。没人发过「决策权清单」,但实现会话自发地:小决定自裁并报备(abandonReason 字段)、边界决定上交(digest 归属)、红线不碰(冻结契约条款)。说明三分法贴合 agent 的自然行为,提示成本低。
- **S3 异构批评者抓到同构互审抓不到的(collab-primitives §2.5 的跨工具主张)**。Codex 的发现几乎全是行为级反例(Git 语义实测、force-with-lease up-to-date、GC 清对象、65/64 分页漏尾),是 Claude 会话互审的盲区。「不撒谎」的保证来自异构,不来自数量。
- **S4 流水线不等待(审查节奏)**。「绿一个发一个、不等 review 继续下一个」连跑 10+ 轮零空转;review 异步回、实现小步改,返工面被 atomic commit 限制住。印证异步协作优于同步会议,也印证了「候选级/架构级分开」能让 90% 的决定不阻塞。
- **S5 单编辑者原则(writeScope / 高扇入 integrator 牵头)**。lifecycle 轨主动认领自己文件的 IO 接线(「这些文件是我写的,单编辑者=零冲突零教学成本」),避免了跨地盘修改。契约的 scope 概念在人肉流程先验证了价值。
- **S6 升级而非私改(R0 纪律)**。commitControl 归属、supersede bug、IO 窗口——所有跨界事项都走「发现 → 上交裁决 → 按裁定执行」,无一例私改他人地盘或私下达成不入账的「共识」。R0 在没有机制强制的情况下靠纪律跑通,说明它符合参与者的自然激励(没人想背锅)。
- **S7 契约条款引用作为沟通压缩**。消息里大量「§4.2 V3」「X2 v3」式引用,双方语境瞬间对齐,无需复述。印证「黑板承载共识」的信息经济学:共识文档越权威,日常消息越便宜。
- **S8 review 的 review(裁决者可错)**。设计侧自己也被 Codex 纠正多次(ALLOC_WINDOW 推论、required 进 specDigest 的错误裁定由下一轮自纠)。验证了对抗层不能省,也验证了「裁决者错误能被流程吸收」——纠错成本 = 一轮消息,而非一次返工。

## 2. 暴露的问题(实现对应机制时的第一优先参考)

- **F1 总线身份不稳定是最大摩擦源**。本场协作里句柄/run id 漂移至少 5 次(Codex 三换 run、实现会话 run 漂移、lifecycle 轨的投递身份 4cee243a 无法反向寻址),设计侧两次发错地址、一次发送失败。直接印证:teammates 名册必须「运行期身份解析 + anchor 锚定」(team-collab §4.1,Codex P2-4),投影 memberId 的稳定性是硬需求不是锦上添花。**实现 C1 时把「句柄漂移后消息仍可达」做进验收。**
- **F2 反向寻址缺失**。收到消息的 from 字段(裸 run id / 投递身份)不保证能用于回复,必须回 peers 名册反查稳定前缀。机制启示:消息信封应携带**可回复的稳定句柄**,不是瞬时身份。给 bus 轨的改进候选。
- **F3 人是静默停摆点(jobStatus.blocked 的真实版)**。commitControl 等 human 放行、IO 接线等用户拍板——两处流水线停在「等人」,且这个状态只存在于会话记忆里,外面看不见。印证 blocked 态 + 卡点名必须可见(投影 jobStatus.note 带节点名正是为此);也提示 repair 的 autoDispatch 闸门要有「谁在等谁、等多久了」的展示。
- **F4 消息预算的现实压力**。全程靠自律「一条消息说完一件事、带齐上下文」,没有爆炸,但消息长度逼近单条上限数次。软预算(R1)在高质量参与者下够用;但参与者质量是前提——机制化记账(C3)的触发条件应是「出现低质量成员」而非「消息多」。
- **F5 跨通道路由混乱**。Claude 跨会话通道与 agenthop 总线并存,同一伙伴在两个通道有不同身份(startup-bus-presence vs 4cee243a),发错通道就失联。印证 team-collab 的判断:成员通信应收敛到单一通道(总线),host 原生通道只作兜底。
- **F6 契约文档的「未跟踪」窗口**。三份契约在 worktree 里当未跟踪文件躺了数小时,期间若 worktree 被清理即全损。教训:**共识文档一产生就入库**(后来 bc47cec 做了)。对应 P2-1 的 evidence 固化原则——落盘 ≠ 持久,入库才算。
- **F7 裁决延迟造成的小返工**。required 字段按我的错误裁定进了 specDigest,一轮后纠回(成本:一个 commit)。若当时实现侧等我复核再提交,可省这个 commit;但那会破坏 S4 的流水线。结论:**小返工是流水线的合理代价**,不要为消灭它引入同步等待——这正是契约「至多一个活 attempt + ABANDONED 不耗预算」设计的现实镜像。

## 3. 对实现排期的直接提示

- 投影(T2 步骤 A)里 memberId 稳定性、jobStatus.blocked 卡点名——F1/F3 的解药,优先级提升。

- bus 轨改进候选:消息信封带稳定回复句柄(F2);此为 bus 层事项,不进 brain/team-collab 契约。
- C3 硬记账的触发条件写成「成员质量」而非「消息量」(F4)。

- F9(元问题,user 点破 2026-10-03):**回路触发依赖 human = 自动化缺口**。F3(静默停摆)记录在案后,活性原则(team-collab §0b)是 user 提醒才立的;§00 本身也是 user 定调的。观察到问题的 agent 没有自发走完「分析→归类→改进」,只走到「记录」。修正见 §4 的处置协议——从本条起,记录而不处置的 F 条目视为未完成的工作,不是完成的笔记。

- S10(2026-10-03,权限边界顶住跨会话转述):R3 立为原则后,协调者把「push+PR」按可撤性归自主类并指令执行;实现会话**正确拒绝**——其 harness 有「push 只在本会话 user 开口时做」的机制门,peer 转述的 user 原则不构成本会话 user 的批准(防 permission laundering)。这正是「机制 > 文档」的活证:原则(文档)没能绕过权限门(机制)。设计启示:R3 在实现里必须长成 per-member 的 decisionRights 配置 + 执行端 admission(open-dots 的 deny-by-default 网关形态),而不是一段所有成员「应当遵守」的文字;成员各自的门彼此独立,协调者的裁定改变不了别人的门——门的变更只能来自门的 owner(那个会话自己的 user)。
- F10(user 二次点破 2026-10-03,协调者自身的活性缺口):**协调者只做事件驱动,无周期巡检 ⇒ 多 agent 空闲、链式隐形等待**。实测:viz 被通知渲染后无回音无人追;f32a0507 等我的「v1 增补定稿」信号,而我在等 viz——我自己刚立的 §0b(每个停顿要可见/期限/旁路)没有适用到我自己身上。1)根因:协调者缺 readyTasks 等价物(空闲成员+无主待办的周期匹配)+「等 X」没有登记期限。2)归类 (a)+(b):当场改——(a) 立「协调者巡检纪律」(见 §4 v3);(b) 机制化 = brain 的 taskPass 本就是这个巡检的自动版,human-协调阶段先用纪律顶,真 dispatcher 上线后由 taskPass 承担。3)落点:本文件 §4 + 协调者行为。4)验证:下次出现「agent 空闲>1 轮而有无主活」即违例。
