# 动态容量设计简报:蜂群按任务规模伸缩,「活造人」(user 定调 2026-10-04)

状态:**设计简报**(R4:先设计后实施;对抗审查后冻结,实现分批)。
user 原话:人物不该固定;不同任务规模需要不同角色;蜂群本来应该是动态的,不是死板的。
现状诚实:五个常驻会话是 dogfood 脚手架——手工扮演「本该按需生成的角色」;规模感知为零(活多了排队不自知,活少了闲人烧上下文)。

## 三层机制(全部接既有零件)

1. **规划期定角色需求**:TaskPlan 节点已有 runtime(ephemeral|durable)/visibility [F];增 rolePro­file{skills, modelTier(接 model-tiering 备忘:kind 定下限+难度上调), expectedParallelism}。规划器(T3 轨道)产出计划时同时产出**人员需求清单**;重大计划的 design 节点审查时顺带审配员(R4 既有流程,零新门)。
2. **容量管理器(新,薄)**:消费两个输入——板/readyTasks 的需求面(什么活缺什么角色) vs 名册+心跳的供给面(谁活着/谁闲/什么档)。规则:
   - 缺口(活等角色超一个 tick)⇒ spawn(R5 白名单通道;ephemeral 默认,受**预算票据**约束——扩编=花钱,票据内自动,超票升 user,R3 三类之一);
   - 过剩(ephemeral 成员无适配活且空闲超阈)⇒ 到期即焚(WORK 分支耐久,焚不丢活;durable 成员只升「建议下班」不强杀);
   - 常驻白名单:协调者+有长期上下文价值者(名单在配置,不在代码)。
3. **角色=配置不=会话**:rolePro­file 是一份说明(提示词模板+模型档+文件域模式),放 ~/.agenthop/swarm/roles/;spawn 即「角色说明+任务信封」实例化。「审查员忙不过来手工找第二个」变成容量管理器按负载自动起第二实例(同角色多实例,R6 既有立场)。

## 3a. 角色本体论(user 终定调 2026-10-04):角色是抽象,与 CLI/session/节点三者全解耦

**角色 = 说明书 + 笔记本 + 域 + 在途义务,四件全是耐久文件,不含任何执行体。** 执行体(某个 claude session、某个 codex 窗口、某台机器上的某进程)只是角色的**当前任期(incumbency)**——任期可以结束、更换、空缺,角色不灭。三层解耦的含义:
- **解耦 CLI**:同一角色今天由 claude 任职、明天由 codex 任职,说明书的 promptTemplate 按工具渲染,笔记本与域不变(对抗审查角色已天然如此:happycapy 与 Work 两个 codex 都任过);
- **解耦 session**:3b 笔记本+接任协议;
- **解耦节点/机器**:角色文件随蜂群数据面走(将来跨机=同一组耐久文件的可达性问题,不是角色问题)。
推论三条:① 板条目的 fitProfile 指向**角色**不指向 session(履历锚=「任过该角色者优先」);② wait 的 owner 字段长期应记角色+当前任期(bus-identity 化身链的上一层:role→incumbent 映射,whois 可答「现在谁任此职」);③ 空缺角色=容量管理器的招聘信号(有 incident 没 medic ⇒ spawn 一个任期)。

## 3b. 角色与 session 解耦:角色笔记本(user 定调 2026-10-04,「session 不可用则角色记忆丢失」的根治)

**问题精确化**:角色目前三层——说明书(roleProfile,已有)、组织记忆(contracts/F账/报告/control-log,已有且天然 session 无关)、**工作记忆(session 私有上下文:决策的为什么、在途思路、踩坑手感)——第三层死绑 session,session 坏=角色失忆**。swarm-resume 只能救「同一 session 还能 resume」的情形,救不了 context 爆掉/会话文件损坏/CLI 升级断代。

**机制:角色笔记本(role notebook)**——`roles/<roleId>.notebook.md`,按**角色**不按 session 存:
- 内容:当前理解快照(我的域里什么状态)、开放线头(没做完的思路)、坑感(哪些地方容易错+为什么)、关键决策索引(指向报告/契约,不复制);
- **更新义务挂在既有检查点**:完成三连的第四行=「笔记本已更新」;重大裁定/交付/合法空闲声明时顺手刷。不另设节拍,零新循环;
- observer 顺手看守:成员有交付但 notebook mtime 久不动 ⇒ 提醒(义务可审计);
- **接任协议**:session 死 ⇒ 按 roleProfile spawn 新会话,boot 包=说明书+笔记本+域内契约+F账相关条——新会话十分钟内达到「接手水平」;bus-identity 化身链把新 session 登记为同一角色的下一任(身份连续,记忆经笔记本移交);
- 诚实边界:笔记本救不了全部隐性上下文——但我们的纪律本来就把关键状态压到盘上(事实在 control-log,裁定在契约,证据在报告),笔记本只需覆盖**残余**:思路与手感。这正是公司制度的本义:**知识属于公司,靠的是文档+交接+组织记忆三件套,而不是祈祷员工不离职**。

验收:杀掉一个有在途单的成员 session(演练),按接任协议 spawn 新任,新任无人工辅导接续其单至交付——「角色不死」实弹。

## 与既有机制的接缝(逐条,防第二账本)
- 执行权仍唯一来自 dispatcher admission(rev3 R2-P1-3 立场):容量管理器只管「有没有人」,不管「谁开工」——spawn 出来的成员照样走板申请/信封收据。
- 预算:CPA 账本(欠条)落地前,票据=次数上限(粗量级);账本接通后升钱额。
- 死亡纪律:ephemeral 焚毁走 generation 隔离(brain 既有);焚毁前 handoff 义务(行为契约)。
- idle-watch/R8-idle 的「ping 成员」在供给过剩时自动变少(没闲人可 ping)——两机制同源不冲突。

## 验收(北极星对账)
同一集群,早上跑 5 节点小活不多花一分钱,下午接 20 节点大活自动扩到需求档,夜里活干完自动缩回常驻核——全程 user 只在「扩编超票据」时被敲一次。
