# 消息交错:为何不可根治,哪些可以(S18 机制简报)

user 2026-10-05:"消息交错老是出现,没有根治的办法吗?"

## 诚实前提
两个独立进程并发写作,消息在途相遇=分布式物理事实,不可消除。
可消灭的是**交错造成的错误决策**。今晚三次交错(⑤裁定×2/死信派单×1)零损失但全靠协调者人肉对账
——把对账动作下沉为代码,即根治「错误」而非「交错」。

## 今晚三次交错的共同解剖
都是同一形状:**一方基于旧状态封稿,而新状态已在途**。
人肉解法都是"比对双方账面→指出谁旧→重发权威版"。机器化三件:

### 1. 裁定/判决的显式版本序(已立,待工具化)
[裁定#R*] 序号已生效(B9 勘误首战)。下沉:S11 消息加可选 `supersedes` 字段
(本消息取代哪条 msgId/序号),消费侧见高序弃低序,不再靠人记时序。
**归宿:bus-reachability 完成后的 S18 小批,validInboxMsg 加字段(可选位,不破 schema)。**

### 2. 封稿前新鲜度检查(纪律→代码)
审查者封稿/实施者开工前,最后一步=冲洗收件箱再确认范围(今晚的错都发生在"写长报告期间来了新消息")。
纪律版立即生效(写进角色档案);代码版=报告提交工具先 flush inbox 并列出未读,有未读先消化。

### 3. 单一事实源替代消息追认(治本,已有架构)
消息交错之所以伤人,是因为**把消息当了权威**。我们本有解药:control-log(CAS+单写者)。
凡"当前权威计级/当前待修清单/当前裁定版本"这类**状态**,归宿不是消息而是耐久单一事实源
(板/PROGRESS/control-log),消息只做"去看第 N 版"的通知。
审查者已自发做了雏形(swarm-review-current.md 索引)。规范化:每单一个状态文件,封稿=写文件,
消息=指针。读者永远读文件最新版,交错的消息自然无害。

## 不做
- 不引入分布式共识/全序广播(杀鸡用牛刀,单机文件系统已给了我们原子 rename 和 CAS);
- 不做"禁止并发工作"的串行化(治病杀人,吞吐就是蜂群存在的理由)。
