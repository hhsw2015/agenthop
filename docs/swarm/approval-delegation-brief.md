# 审批代理:成员弹窗不再等人(S19 简报,user 定调 2026-10-05)

user 原话要义:成员(如 Claude Code)弹出选项界面=在等审批。它该发消息给协调者,**协调者可代理
的决定就代理掉;真正需要 user 的,才到 user**——这才是数字员工的本义。否则 user 没看到弹窗,
它就卡很久。

## 已有的半边(F33 盘点:别重造)
- PermissionRequest hook 已在:弹窗瞬间成员状态→blocked,进 presence/roster(agents.ts 已接)。
- idle-watch/sweep 已消费 blocked 状态;协调者能看见"谁卡着"。
- **缺的半边:blocked 只是状态,不带「卡在什么问题上、有哪些选项」的内容;协调者看见卡了,
  却无从代理——只能像 user 一样干瞪眼。**

## 机制(三层,复用已有零件)

### 1. 弹窗内容进协调者收件箱(新,核心)
PermissionRequest hook 升级:除打 blocked 状态外,把**弹窗语义**(工具名/命令摘要/选项列表/
会话 sid)写成 S11 消息投协调者耐久箱(taskRef=approval/<sid>,title=一句白话"X 请求做 Y")。
hook 是 shell 命令,写文件零依赖——复用 writeInbox 格式即可。

### 2. 协调者审批矩阵(裁定权分层,R3 两层判据沿用)
收到审批请求,按既有三门分流:
- **可代理**(绝大多数):可撤销 + 域内 + 不花钱不改原则 ⇒ 协调者按派单上下文裁定,
  回消息给成员(成员收到后自行在界面选择对应项;若 CLI 支持无头审批则直接注入)。
  决策留痕 control-log(谁代批了什么,事后可审)。
- **须 user**(三门:改原则/花钱/不可逆):打包成一条白话呈批(S15),连同协调者的推荐与理由,
  经既有渠道给 user;**同时给成员一个带默认的期限**(R3-b 同款:超时走保守默认,不永久卡)。
- **不确定**:当保守侧处理=升 user。
### 3. 防呆底线
- 代理审批≠绕权限:协调者只能替 user 选「user 本来会选的安全项」,任何提权类选项(bypass
  permissions/危险模式)永不代理,直升 user。
- 审批请求也走 sweep deadline:无人处置的审批 N 分钟后升级(escalate),绝不静默卡死——
  这正是 user 点名的「卡很久」的机制性消灭。
- 成员侧不改 CLI 本体:hook 是 Claude Code 原生扩展点;Codex 侧等它的 hook 面(有 PermissionRequest
  等价物即同法接入,无则先靠 blocked 状态+人工)。

## 与既有件的关系
- 这是 §0b「协调者=判断面」的最后一块拼图:派活/收活/裁争议都已机制化,审批是唯一还直通 user 的。
- cluster-medic 的 runbook 思想同源:高频审批模式沉淀为预授权规则(「此类命令以后自动批」),
  就是 F→runbook 管线在审批域的应用——第一期先人工代理积累样本,预授权规则等真实分布出来再定。

## S19-b 增补(humanlayer 对照研究产出,2026-10-05;详见 docs/research/humanlayer-eval.md)

对照结论先行:humanlayer 两代(旧审批 SDK 已弃用/新编排产品)都把人放在**每个**审批环上;
S19 的协调者代批层(可撤+域内自动代,只三门到 user)是其从未有过的——外部对照反印证本简报新意。

四个它有/双方共缺的边角,纳入实现面(仍第一批排期,不扩 scope 只补语义):
1. **主动问人原语**(human_as_tool 式):S19 原稿全被动(等弹窗);补「成员可主动发起问询」
   ——其实我们已有 R3-b 问询带默认,此处只需打通:成员问询也走审批收件箱同通道,不另造。
2. **粒度到工具+参数**:预授权规则(未来 F→runbook 层)的键=工具+参数模式,不是裸工具名。
3. **拒绝带可执行理由**:协调者拒绝/user 拒绝时,回执必含「拒因+改法」(S15 同款:可直接行动)。
4. **撤回时窗**(双方共缺,user 点名过的形状):已代批但未执行的决定,显式可撤;
   执行开始即不可撤(转事后追认面)。代批留痕里加 executedAt,撤回=该字段为空时有效。
批量预授权档维持 S19 原稿的保守位(等真实分布,F→runbook 管线)。
