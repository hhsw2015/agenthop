## 结论

1. **方向重合度极高,是第三个独立趋同样本**(comma、openrig 之后)。用户的一人公司/数字员工
   愿景再获外部印证,且该视频证明这套叙事有受众。
2. 她的系统是**我们的提示词层原型**:每个概念我们都有机制化版本。F23(口头满载 vs 实际空闲)、
   F25(完成不上行)、F29(判决不下行)就是提示词承载必然撞上的三面墙——她的观众将来会踩同样的坑。
3. **可借之点(一个)**:"两类请求"分类法——做工作的请求 vs 建能力的请求。干净的任务本体论,
   T3 planner 的 actionKind/板项类型可吸收这个一级区分;capability 类请求天然对应我们的
   IOU/免疫管线产物。
4. 不借:飞书作共同记录(无 CAS/单写者,与 projection 契约冲突);提示词心跳(已被 sweep 取代)。

## 补(同频道前两集:DevDay/Dot 综述、本地+云端双助手)

2. **Token 套利观察**(把活路由给云端 Dot 省本地额度):本质是"按资源池路由任务"。
   印证 CPA 成本台账(头号 IOU)的必要——没有成本账,这类路由决策无依据。
   也呼应 model-tiering(kind 定档下限)。不新开单,记在 CPA IOU 上。
3. **战略面**:OpenAI 在把 Dot+云环境+GitHub+共享空间拼成平台级工作系统,
   与我们同构。差异=我们机制在自己手里(control-log/CAS/审查/免疫),供应商中立;
   节点今天是 Claude/Codex,明天可以是 Dot。用户"一群 Dot 的公司"的框架
   反而被产品方追认了。

## 补3:Dot 官方 launch demo 逐段解剖(2026-10-05,user 供料)

场景:老板打电话给 Dot——订明天 LA 差旅(航班/酒店/截图/地图),中途追加两件:
用户反馈分析+工作流显式化、Slack 未回消息起草。全程语音,人只做选择和追加。

### 对我们设计的印证(逐段)
1. **「我还要核实结账总价和政策」「我先把这个叫作最大主题前,先查完整排名」**——Dot 全程区分
   「已核实/待核实」,不冒称:= 我们的三态诚实+「验证边界」纪律(S14 未验证面)。官方把它做成了
   **话术层的产品特性**,我们做在报告形制里。同构。
2. **「现在的 capture workflow 是什么?」→Dot 如实念出手动流程并点出『ticket 对账仍不完整』**
   ——自报系统边界而非装完美:= 我们的 dogfood/诚实停放文化。
3. **落地时间预算「30-45 出机场+45-75 车程」→主动建议「中午前落地我更放心」**——不只执行,
   给判断建议但决定权在人:= 我们呈批件「协调者推荐+理由,裁决归 user」的 S19 形制。
4. **反馈环「PR 落地→回 Slack 链 PR→请用户重试→retest 确认闭环」+「retest 一直不稳定」**
   ——这就是我们的完成槽/验收观(完成=验收过,不是自报;F20)在客服域的版本。
5. **demo 本身演的最大主题竟是「reliability:dot 看着活着但不回话/工具失联」**——OpenAI 的
   头号用户痛点正是我们 F30/F34/bus-reachability 整个星期在根治的东西(活着≠可达≠在干活)。
   我们的 presence/恢复事实/卡死检测先于他们的产品痛点清单。

### 可借的真东西(一件)
**多任务并行对话形制**:电话里三个任务流(差旅/反馈分析/Slack 草稿)交错推进,Dot 维持各自
进度互不丢(「我还在抓截图」「我在后台跑排名」),人随时插入新任务。我们的协调者↔user 面
今天是回合制的;装机后若接语音/实时面(CPA 有 realtime 模型,S17 已入盘),这个「多线保持+
随时插入」的对话形制是现成参考。不是现在做,是 approval-delegation+语音面那天的输入。

### 不借
话术润色(「Let me align that up for you」类)——产品人格面,非机制;我们的 S15 白话纪律已覆盖
实质(说清楚在做什么、什么没验证)。

## 补4:opencode-gpt-live 参考评估(2026-10-05,user 供料,语音面设计输入)

malhashemi/opencode-gpt-live:OpenCode 插件,`/voice` 即与会话实时语音通话(GPT-Live 实时模型,
走用户已有 ChatGPT 订阅零 API key)。32 星新项目但工程完整(CI/跨平台/本地回声消除)。

**正中我们语音面的四个设计问题,它各给了一个已验证答案:**
1. 插话时机 →「talk while it works」:请求排队进会话,人随时问进度/改方向/叫停,干活不断线。
2. **语音审批** →「approve by voice」:会话弹权限请求时,语音念出请求、人口头答、插件代点
   ——这正是 S19 审批代理的语音终端形态!(S19 是协调者代批+三门升 user;它是把「升 user」
   这一跳做成了语音,两者互补不冲突。)
3. 会话连续性 → 每会话一条语音长对话,下次通话记得上次。
4. 打扰工程 → 本地回声消除/通话时压低其他应用音量——打扰礼仪做到了系统音频层。
**与我们的接法差异**:它绑 OpenCode+GPT-Live+ChatGPT 订阅;我们的语音面应绑协调者+CPA 实时
模型(S17 清单:gemini-3.8-live/gpt-realtime-2/qwen-omni,BYOK 走自己账)。**借形制不借栈**:
排队进会话、语音读权限请求、每会话一条长对话、音频打扰工程四条照搬;栈换成 MCP 工具面+CPA。
**一条不借的形制(user 裁定 2026-10-05,压倒上文第3条)**:它是「每个会话一条语音线」——
那是它栈的产物(插件绑单会话)。我们的宪法是单一接口:**user 只和协调者一条语音线,永不直连
成员会话**。成员的进度/弹窗/结果全部经耐久箱汇到协调者,由协调者在这一条线上代表全蜂群说话
(多流保持/插话时机/汇聚压缩本来就是协调者职责,Dot demo 同款)。「会话连续性」相应改写为
「协调者的语音线跨通话连续」。语音审批同理:弹窗语义→协调者箱(S19 既定)→可代理的代理掉,
三门才在这条唯一语音线上念给 user。
**定位**:语音面批(装机门后,与 approval-delegation 同批)的首要实现参考,届时先读它的
plugin 源码(TypeScript,MIT)看排队与审批桥的接线——但拓扑按上条:一条线,接协调者。
记入 S17/S19 交叉输入,今天不动手。
